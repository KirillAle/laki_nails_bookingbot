# Общая схема: запись клиента и управление мастером

## 1. Роли и кто что делает

| Роль    | Сейчас | Позже (когда появится Админ) |
|---------|--------|------------------------------|
| Клиент  | Выбор процедур → выбор периода → выбор слота → запись | Без изменений |
| Мастер  | Открытие записи на месяц, график, блокировки, перенос/отмена записей | Только просмотр записей на сегодня и на другие дни |
| Админ   | — | Открытие месяцев, блокировки, переносы, отмены (всё админское) |

---

## 2. Модель данных (как это ложится на текущую БД)

### 2.1 Процедуры (таблица `procedure`)

- **Идея:** 2 базовые процедуры × 4 варианта сложности = **8 записей** в `procedure`.
- Поля:
  - `procedure_type` — тип: `"Маникюр"` / `"Педикюр"`.
  - `procedure_subtype` — сложность (например: `"Простой"`, `"Стандарт"`, `"Сложный"`, `"Премиум"`).
  - `duration_slot` — длина в тайм-слотах (1 слот = 15 мин по `time_slot`).
  - `price`, `is_active`.

Клиент в боте выбирает одну или две процедуры из этих 8 (индикатор «выбрано/не выбрано»).

### 2.2 Расписание и слоты (таблицы `master_schedule`, `master_time_block`, `time_slot`)

- **master_schedule:** один ряд = один рабочий день мастера (дата + время начала/конца дня + перерыв).  
  Либо (если у вас один ряд = один слот) один ряд = один бронируемый слот на дату.
- **master_time_block:** блокировки (выходной, обед, личное время) — в эти интервалы запись недоступна.
- **time_slot:** эталон слота (например 15 мин). Используется для расчёта длительности процедур и шага слотов.

Важно зафиксировать в коде: **одна запись в `master_schedule` = один день** (дата + время начала/конца дня + перерыв) или **один слот** (конкретное окно времени). От этого зависит, как считаем «свободные окна» (генерация из дня по шагу `time_slot` или выбор из готовых строк).

---

### Вариант А vs Вариант Б — разница и что выбрать

**Суть разницы:** что храним в одной строке `master_schedule` — целый рабочий день или одно маленькое «окно» (слот).

| | Вариант А: 1 строка = 1 день | Вариант Б: 1 строка = 1 слот |
|--|------------------------------|-------------------------------|
| **Одна строка `master_schedule`** | Один день: дата + «работаю 9:00–18:00, перерыв 13:00–14:00». | Одно окно: например «15 марта, 9:00–9:15». |
| **Сколько строк на один день?** | Одна строка на день. | Много строк (на каждый слот по 15 мин: 9:00, 9:15, 9:30, …). |
| **Откуда берутся слоты 9:00, 9:15, …?** | Считаются в коде: от `time_start` до `time_end` шагом 15 мин, минус перерыв и блокировки. | Уже лежат в БД — каждая строка и есть слот. |
| **Что хранит `booking`?** | `schedule_id` = эта строка (день) + `start_time` = начало (например 9:30). | `schedule_id` = эта строка (конкретный слот 9:00–9:15). `start_time` можно не использовать или дублировать. |
| **«Слот занят» как проверяем?** | Есть ли запись в `booking` с этим `schedule_id` и этим `start_time`. | Есть ли запись в `booking` с этим `schedule_id` (один слот = одна запись). |

**На что это влияет:**

- **Открытие записи на месяц:**  
  - **А:** создаёшь 20–31 строку (по одной на каждый рабочий день месяца).  
  - **Б:** создаёшь сотни строк (каждый день × каждый слот 15 мин).  
- **Смена длительности слота (например 15 → 30 мин):**  
  - **А:** меняешь только логику в коде (шаг по `time_slot`).  
  - **Б:** перестраиваешь кучу строк в БД.  
- **Блокировка «сегодня с 14:00 до 16:00»:**  
  - **А:** одна запись в `master_time_block`; при расчёте слотов просто вычитаем этот интервал.  
  - **Б:** можно тоже через `master_time_block`; слоты в этом интервале не показываем.  
- **Перенос записи:**  
  - **А:** меняем у `booking` только `start_time` (и при необходимости `schedule_id`, если перенос на другой день).  
  - **Б:** меняем `schedule_id` на другую строку-слот.

**Рекомендация: Вариант А (1 строка = 1 день).**

1. Твоя таблица `master_schedule` уже под это заточена: есть `date`, `time_start`, `time_end`, `break_start`, `break_end` — это описание дня, а не одного окна в 15 минут.  
2. Меньше данных: на месяц десятки строк, а не тысячи.  
3. Гибче: длительность слота (15/30 мин) и правила считаются в коде, без миграций и перезаписи слотов в БД.  
4. В `booking` уже есть `schedule_id` и `start_time` — этого достаточно: слот = пара (день = `schedule_id`, начало = `start_time`).

**Что поправить в коде под Вариант А:**  
Сейчас `findByScheduleId` возвращает одно бронирование (`firstOrNull`). Для варианта А в один день может быть несколько записей (разные `start_time`). Нужно:  
- либо переименовать/добавить метод «все бронирования на этот день»: например `findByScheduleId(scheduleId)` возвращает `List<BookingEntity>`;  
- и проверка «слот свободен» = нет бронирования с этим `schedule_id` и этим `start_time` (при необходимости — добавить `findByScheduleIdAndStartTime`).

### 2.3 Бронирование (таблица `booking`)

- Один приход клиента «маникюр + педикюр» = **два бронирования** (два ряда в `booking`):
  - оба с одним `client_id`;
  - два разных `procedure_id` (маникюр и педикюр);
  - два слота подряд: у первого `start_time` = T, у второго = T + длительность первой процедуры.
- Логика «сразу две процедуры» в боте: ищем один слот длиной (duration1 + duration2) или предлагаем два отдельных слота.

### 2.4 «Открытая запись на месяц»

- **Вариант А:** мастер «открывает месяц» = создаются/обновляются строки в `master_schedule` на все нужные даты (с полями дня: время начала/конца, перерыв). Слоты на день считаются в коде по шагу из `time_slot` и с учётом `master_time_block`.
- **Вариант Б:** есть отдельная сущность «период открытой записи» (например таблица `booking_period`: master_id, date_from, date_to, is_open). Тогда «открытые даты» = пересечение этого периода с датами, на которые есть `master_schedule`.

Для гибкости можно позже ввести `booking_period`; пока достаточно «есть master_schedule на дату» = запись на эту дату открыта.

## 3. Сценарий клиента (пошагово)

### Шаг 1: Старт и выбор процедур

- Клиент заходит в бота, нажимает **Старт** (уже есть: сохранение в `account_form` с ролью CLIENT).
- Показываем **8 кнопок** (2 процедуры × 4 сложности), с индикатором «выбрано / не выбрано».
- Клиент может выбрать:
  - только маникюр (1 из 4 вариантов),
  - только педикюр (1 из 4),
  - или обе процедуры (по 1 варианту сложности у каждой).
- Кнопка **«Продолжить»** активна, когда выбрана хотя бы одна процедура.

### Шаг 2: Выбор периода (30 дней вперёд, с учётом текущего дня и месяца)

- По нажатию **«Продолжить»** показываем кнопки с **интервалами дат**, например:
  - «1–10» (текущего или следующего месяца),
  - «11–20»,
  - «21–31» (или «21–28/29/30/31» в зависимости от длины месяца).
- Правила:
  - Текущая дата клиента = **сегодня**.
  - Если мастер **ещё не открыл следующий месяц** — показываем только даты в **текущем открытом периоде** (те даты, на которые есть `master_schedule` и они ≥ сегодня).
  - Пример: клиент зашёл **19-го**. Открыты только даты до конца месяца. Показываем кнопки «19–20» (остаток 11–20) и «21–31» (или до конца месяца).
- В зависимости от длины месяца и открытых дат интервалы считаются в коде (календарь месяца, разбиение на 1–10, 11–20, 21–31).

### Шаг 3: Выбор интервала и свободных окон

- Клиент нажимает интервал (например «21–31»).
- Бот считает **свободные слоты** на эти даты:
  - по каждому дню из интервала: из `master_schedule` (рабочий день) вычитаем `master_time_block` и уже занятые `booking`;
  - шаг слотов из `time_slot` (15 мин).
- Если выбраны **две процедуры**:
  - приоритет: показать слоты, куда **влезают обе подряд** (длина = duration1 + duration2).
  - если таких нет — предложить **разбить на два времени** (два слота).
- Клиент выбирает одно окно (или два, если разбито).

### Шаг 4: Подтверждение и запись

- Показываем сводку: процедуры, дата, время, цена.
- Подтверждение → создаём в БД:
  - один или два `booking` (client_id, выбранные procedure_id, слот(ы), price_snapshot, status = PENDING или CONFIRMED по вашей логике).

## 4. Сценарий мастера (сейчас и потом)

### 4.1 Сейчас (мастер = «почти админ»)

- **Открыть запись на месяц:** выбор месяца → создание/обновление `master_schedule` на каждую нужную дату (время начала/конца дня, перерыв). Так «открывается» период.
- **График:** те же `master_schedule` (при необходимости правка времени начала/конца, перерыва).
- **Закрыть дни/часы:** создание `master_time_block` (дата, start_time, end_time, reason). В этих интервалах слоты не показывать клиенту и не давать записываться.
- **Перенос клиента:** изменение у существующего `booking` привязки к слоту/времени (или создание нового бронирования и отмена старого — в зависимости от того, храните ли слот как отдельную сущность или только start_time в `booking`).
- **Отмена/удаление записей:** обновление статуса бронирования (CANCELLED) или удаление записи из `booking` (если по бизнес-правилам так заложено).

### 4.2 Позже (когда появится роль Админ)

- **Админ:** все действия выше (открытие месяца, блокировки, переносы, отмены) выполняет только он.
- **Мастер:** только просмотр — «записи на сегодня», «записи на выбранный день», «кто записан» (без изменения графика и записей).

Роли хранятся в `account_form.role`: CLIENT, MASTER, ADMIN.

## 5. Гибкий подход в коде

### 5.1 Единая логика поверх БД

- **Сервисы (не бот):** вся логика «кто может записаться куда» живёт в сервисах (например `BookingService`, `MasterScheduleService`, отдельный `SlotAvailabilityService`):
  - расчёт свободных слотов по датам;
  - проверка «влезают ли две процедуры подряд»;
  - создание одного/двух бронирований.
- **Бот и (потом) сайт/приложение** только вызывают эти сервисы или REST API, построенный поверх них. Так сценарий клиента и мастера остаётся одним и тем же, меняется только интерфейс (кнопки в боте или форма на сайте).

### 5.2 Что реализовать по шагам

1. **Процедуры:** заполнить/проверить 8 записей в `procedure` (2 типа × 4 сложности).
2. **Слоты:** зафиксировать модель (одна строка `master_schedule` = день или слот) и написать расчёт свободных слотов на период с учётом `master_time_block` и существующих `booking`.
3. **Клиент в боте:** состояния (выбор процедур → выбор периода → выбор слота → подтверждение), кнопки 1–10 / 11–20 / 21–31 с учётом текущей даты и открытых дат.
4. **Мастер в боте:** меню мастера — открытие месяца, блокировки, просмотр записей, перенос/отмена (пока всё у мастера).
5. **Позже:** роль ADMIN в `account_form`, разделение прав — админские действия только у админа, у мастера только просмотр.

### 5.3 Удобство для клиента

- Понятные подписи кнопок (название процедуры + сложность).
- Явный индикатор выбранного (галочка / «Выбрано»).
- Интервалы дат зависят от месяца и от того, на какой день клиент зашёл.
- При двух процедурах сначала предлагать один слот «подряд», потом вариант «в разное время».

## 6. Краткая схема по таблицам

| Таблица / сущность   | Использование в сценарии |
|----------------------|--------------------------|
| `account_form`       | Роли CLIENT / MASTER / ADMIN, данные пользователя после /start. |
| `procedure`          | 8 вариантов (2 типа × 4 сложности), выбор клиента, длительность и цена. |
| `master_schedule`    | Рабочие дни мастера (или отдельные слоты) — основа для «открытой записи» и расчёта слотов. |
| `master_time_block`  | Блокировки дней/часов — исключаются из доступных слотов. |
| `master_procedure`   | Какие процедуры делает мастер (фильтр «кто может записаться к кому»). |
| `time_slot`          | Эталон шага (15 мин), длительность процедур в слотах. |
| `booking`            | Одна запись = одна процедура в одном слоте; «маникюр + педикюр» = два booking. |

Дальше можно разнести реализацию по этапам: сначала расчёт слотов и проверки в сервисах, затем кнопки и состояния в боте по этой схеме.
